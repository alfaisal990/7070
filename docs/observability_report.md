# تقرير الرصد والمراقبة (Observability Report) - Phoenix AI

يوضح هذا التقرير نظام الرصد والمراقبة الشامل الذي تم بناؤه وتفعيله لمنصة **Phoenix AI** لضمان استقرار التشغيل، وتتبع الأخطاء، وإصدار المقاييس التشغيلية المناسبة لبيئات الإنتاج الفعلي.

## 1. تسجيل الأحداث المهيكل (Structured Logging)

تم التخلي عن تسجيل الأحداث النصي التقليدي غير المنظم، واعتماد التسجيل المهيكل بصيغة **JSON** لتسهيل الفهرسة والتحليل بواسطة خوادم تجميع السجلات (مثل ELK Stack أو Grafana Loki).

### تفاصيل الإعداد:
* **تنسيق السجل**: يتم تصدير كل حدث في سطر واحد يحتوي على الحقول الأساسية:
  * `timestamp`: التوقيت بصيغة ISO-8601.
  * `level`: مستوى السجل (INFO, WARNING, ERROR, CRITICAL).
  * `logger`: اسم المكون البرمجي المصدر للحدث.
  * `message`: نص الحدث الأساسي.
  * `request_id`: المعرف الفريد للطلب (إن وجد) لتتبع دورة الحياة.
  * `exception`: تفاصيل الخطأ وتتبع المكدس (Traceback) في حال حدوث استثناء.
* **إعادة توجيه سجلات uvicorn**: تم تهيئة خادم الويب وجسر ASGI لتمرير كافة سجلات الطلبات والأخطاء عبر المنسق المهيكل لتوحيد تنسيق المخرجات.
* **المسار البرمجي المطبق**: [logging.py](file:///c:/Users/1/Desktop/7070/ai_project/utils/logging.py)

## 2. تتبع الطلبات بواسطة المعرفات الفريدة (Request IDs)

لتتبع سير الطلبات عبر الطبقات المختلفة، تم بناء برمجية وسيطة (Middleware) تقوم بالآتي:
1. اعتراض الطلب الوارد والبحث عن ترويسة `X-Request-ID`.
2. في حال عدم وجودها، يتم توليد معرف فريد جديد (UUIDv4).
3. تخزين المعرف في متغير سياقي آمن لتعدد المهام (`contextvars.ContextVar`) ليكون متاحاً لجميع سجلات الأحداث خلال معالجة الطلب.
4. إدراج المعرف في ترويسة الاستجابة المرسلة للعميل `X-Request-ID` لتسهيل مضاهاة المشاكل من جهة المستخدم النهائي مع سجلات الخادم.

## 3. مقاييس الأداء لـ Prometheus (Prometheus Metrics)

تم إعداد نقطة نهاية مخصصة بالمسار `/metrics` متوافقة مع تنسيق النصوص القياسي لـ Prometheus لتمكين خوادم المراقبة من جمع المؤشرات التشغيلية للمنصة دورياً.

### المقاييس التي يتم تتبعها:
| المقياس التشغيلي | النوع | الوصف |
| :--- | :--- | :--- |
| `phoenix_api_requests_total` | Counter | العدد الإجمالي للطلبات مقسمة حسب النتيجة (all, success, failed). |
| `phoenix_api_active_requests` | Gauge | عدد الطلبات النشطة التي تتم معالجتها حالياً. |
| `phoenix_api_latency_seconds_total` | Counter | زمن الاستجابة الإجمالي التراكمي بالثواني. |
| `phoenix_llm_tokens_generated_total` | Counter | عدد الرموز (Tokens) المولدة بواسطة النموذج اللغوي. |
| `phoenix_llm_prefill_seconds_total` | Counter | وقت المعالجة التراكمي لمرحلة التجهيز (Prefill Phase). |
| `phoenix_llm_decode_seconds_total` | Counter | وقت المعالجة التراكمي لمرحلة فك الرموز (Decode Phase). |
| `phoenix_llm_generation_sessions_total`| Counter | إجمالي جلسات التوليد اللغوي التي تم إطلاقها. |

## 4. فحوصات الصحة والجاهزية والحياة (Health, Readiness, & Liveness Checks)

تم تزويد المنصة بثلاثة مستويات من نقاط الفحص للتوافق الكامل مع بيئات الحاويات و Kubernetes:

### أ. فحص الصحة العام (`/api/health`)
يقدم تفاصيل تقنية حول المنصة:
* حالة الاتصال والنسخة الحالية.
* وقت تشغيل المنصة (Uptime) بالثواني.
* تفاصيل النموذج اللغوي (اسم النموذج، عدد البارامترات، جهاز التشغيل CPU/CUDA، وحالة التدريب).
* إحصائيات بنك الذاكرة المتجهية (العدد الإجمالي للمستندات).
* حجم مفردات المفسر اللغوي (Tokenizer).

### ب. فحص الحياة (`/api/health/liveness`)
* **الهدف**: التحقق من أن خادم التطبيق يعمل ومستجيب.
* **المخرج**: `{"status": "alive", "uptime_seconds": ...}` برمز استجابة `200 OK`. في حال فشل الاستجابة، يقوم نظام التشغيل أو Kubernetes بإعادة تشغيل الحاوية تلقائياً.

### ج. فحص الجاهزية (`/api/health/readiness`)
* **الهدف**: التحقق من أن كافة الأنظمة اللغوية وبنك الذاكرة والمحرك قد تم تحميلها بالكامل في الذاكرة وهي جاهزة لاستقبال المعالجات.
* **المحكات المتبعة**: التحقق من أن الكائنات التالية ليست فارغة: `model`, `tokenizer`, `memory_store`, `engine`.
* **المخرج**: استجابة `200 OK` بالهيكل التالي عند الجاهزية:
  ```json
  {
    "status": "ready",
    "components": {
      "model": true,
      "tokenizer": true,
      "memory_store": true,
      "engine": true
    }
  }
  ```
  وفي حال تعثر تحميل أي مكون، يتم إرجاع رمز الخطأ `503 Service Unavailable`.
